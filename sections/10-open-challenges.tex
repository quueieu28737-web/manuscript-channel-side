Shadow state has three possible implementations. \textbf{(1) Authorized reads and verified no-ops} use the backend with discarded responses; idempotence alone does not preserve state. \textbf{(2) Provider-supported isolation} includes Kubernetes server dry-run, separate Stripe sandboxes and transactional rollback \cite{kubernetesdryrun,stripesandboxes,postgresrollback}. These have different semantics: for example, sequence changes can survive rollback \cite{postgressequences}. \textbf{(3) A trusted tool gateway} authenticates cover markers and routes shadow writes to an isolated executor. Our local measurements implement the gateway path; the provider-specific paths identify deployments for follow-up measurement.

The trusted gateway/executor can identify cover. Protection ends at exposed markers, routing branches or commit logs; it does not protect against that principal. On the ingress link, the inexpensive WF adaptations are relevant competitors. At a restricted dispatch view, hiding call profiles additionally requires marker/routing isolation. The choice therefore follows the required observation boundary. Cover also consumes quotas and shared capacity; admission budgets, backpressure and separate credentials must prevent overload or accidental live writes.

\subsection{Ethics and artifact scope}\label{sec:ethics}
Executions use cloned public benchmark databases and loopback sockets; model requests contain public tasks and simulated interactions. No production account is modified or third-party service probed for a vulnerability. Stakeholders include paying tenants, shared-capacity providers and people affected by state changes. Other-account cancellation is a simulator control. Released inference code can support surveillance; examples use public/synthetic identities and controlled endpoints. Bot-detection evasion has a different authorization boundary \cite{zhu2026turing,jeong2026wra}.

AI assisted candidate-field extraction, implementation, source reconciliation and prose revision. Authors retain responsibility for the source-linked comparison and its interpretation. Saved-output replay, model-generated trajectories and measured local TLS are distinguished throughout. The artifact archives source locators, decisions, observations, calibration and executable checks. An anonymous submission snapshot must omit identity metadata and development history; the separate submission checklist records the AI-use disclosure and author review required at registration.

\subsection{Threats to validity and scope of evidence}\label{sec:validity}
\paragraph{Statistical scope}
The BA/AUROC screen is an engineering threshold, not a security definition. No joint design confirms the two-target absolute criterion; paired reductions establish improvements against specified fitted suites. Intervals reselect the suite maximum but omit retraining uncertainty. The frozen split has 5/7 positive customers; the full cohort has 14/18. Repeats add execution coverage. Reference calibration uses the known population. Real-agent calibration precedes held-out collection, but developers knew the task set; cross-fit, timing and transfer extensions are exploratory.

\paragraph{Targets and deployment utility}
Operation targets are coupled to intended actions; localization identifies their metadata signature. The same-operation attribute diagnostic is inconclusive (Appendix~\ref{app:experiments}). Original agent reward, defended logical conformance and live prefix-shadow utility are distinct outcomes. Full framing/flush utility remains unmeasured. Local RPC timing excludes LLM generation and WAN transit. WF adapters support matched metadata comparisons; original-protocol equivalence and equal-utility deployment comparisons remain open.

\paragraph{External validity}
The four mutable model aliases operate in one retail environment with separate user-simulator contexts. Luna has 29 training episodes per prompt; MiniMax and GLM each have 69 training tasks. Transfer matrices and live planning reuse known customers. Fresh customers, fixed weights, verified cross-provider identities, new environments and provider-backend measurements define the next validation axes.
